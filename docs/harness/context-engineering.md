# 上下文工程（Context Engineering）

> 目标：让 Agent 只加载完成当前任务所需的、可验证的最新信息。

## 1. 知识来源

### 1.1 事实优先级

| 优先级 | 来源 | 用途 |
|-------|------|------|
| 1 | 当前 checkout 的代码、配置、测试、CI | 判断真实行为和版本 |
| 2 | 最近的 `AGENTS.md` | 组件边界、命令根、验证合同 |
| 3 | `docs/harness/`、`docs/standards/` | 全局治理与技术规范 |
| 4 | `docs/`、`specs/` | 领域说明、设计和需求背景 |
| 5 | README、提交历史、PR/Issue | 补充背景和变更原因 |

若来源冲突，优先采用更接近代码、更近期且有测试或 CI 支撑的来源，并在结果中指出冲突。

### 1.2 关键知识位置

| 知识 | 位置 | 更新时机 |
|------|------|---------|
| 项目全局入口 | `AGENTS.md` | 组件、关系或全局规则变化 |
| 组件运行时和架构 | `src/*/AGENTS.md`、`test-bdd/AGENTS.md` | 组件行为或命令变化 |
| Dashboard 层级约束 | `src/dashboard/apigateway/apigateway/**/AGENTS.md` | 分层职责变化 |
| AI Gateway 领域模型 | `docs/ai-gateway-models.md` | 模型或协议变化 |
| BDD 契约 | `specs/`、`test-bdd/cases/` | 测试模型或用例变化 |
| 构建和依赖 | 各组件 Makefile、`go.mod`、`pyproject.toml`、`package.json` | 工具链变化 |
| CI 行为 | `.github/workflows/` | 门禁变化 |

维护责任人为对应组件的变更作者与 Reviewer；固定负责人尚待团队确认。

### 1.3 禁止作为唯一依据

- 未进入版本控制的聊天记录、口头约定和本地临时文件。
- 与当前 checkout 不匹配的旧计划、旧 PR 评论或旧生成文档。
- 未读取实现或文档即凭记忆推断的第三方 API。

## 2. 渐进式披露

```text
第一层：根 AGENTS.md
  -> 识别组件、系统关系和文档入口
第二层：组件 AGENTS.md + docs/harness/README.md
  -> 获取局部架构、命令和治理规则
第三层：目标代码、测试、配置、spec 和深度文档
  -> 只读取与当前行为直接相关的内容
```

- 大文件先查目录、标题或符号，再读取相关区段。
- 跨组件任务先画清生产者/消费者链路，再扩大读取范围。
- 已验证且工作树未变化的静态上下文可复用；git 状态、diff 和测试证据按需刷新。

## 3. 动态上下文

| 数据 | 来源 | 获取原则 |
|------|------|---------|
| 工作树和分支 | `git status`、`git rev-parse`、`git worktree list` | 修改、提交、发布前刷新 |
| 测试与 lint | 组件 Makefile/包管理命令 | 从目标组件目录执行 |
| 日志 | 组件运行日志、测试输出 | 从用户给出的精确日志开始 |
| 指标 | Prometheus `/metrics` | 仅在有环境访问权限时读取 |
| Trace | OpenTelemetry 配置和后端 | 不假设已启用，先查配置 |
| 错误上报 | Sentry 配置 | 不输出 DSN、Token 或敏感上下文 |

生产数据库、etcd、TAPD 和在线环境属于外部状态；没有明确授权和凭据时只做本地只读分析。

## 4. 更新机制

1. 变更架构、命令、目录、接口或验证门禁时识别受影响文档。
2. 在同一 PR 更新最近的 `AGENTS.md` 或对应 Harness/技术文档。
3. 使用路径、锚点和命令检查验证引用。
4. 若代码与文档冲突，先以代码和测试为证据，再修正文档。

## 检查清单

- [ ] 已读取根规则和目标路径最近的 `AGENTS.md`
- [ ] 已确认仓库、worktree、分支和目标 revision
- [ ] 已从用户指定的路径、日志、URL、提交或报告开始调查
- [ ] 已区分当前事实、历史背景和待确认信息
- [ ] 跨组件扩展范围有明确生产者/消费者证据
- [ ] 变更影响文档时已同步更新
